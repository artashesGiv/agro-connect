# Изображения в Android-приложении: информация для бэкенда

Дата: 12 сентября 2026 года.

## Проблема и границы проверки

Сообщённый симптом: при получении изображения приходит пустой URL.
Ниже описан фактический код клиента и контракт установленного Supabase SDK.
Ответ проблемного запроса с работающего окружения не снят: конкретная причина
на бэкенде пока не подтверждена. Все JSON-примеры ниже иллюстративные, а не
снятые ответы сервера. Изменений в код приложения не внесено.

**Главное:** ответ с постами содержит путь к файлу, а не готовый URL.
Временную ссылку приложение получает отдельным запросом в приватный бакет
`post-media`. При отсутствии ссылки клиент молча исключает фото из отображения.

## 1. Получение постов и путей

Клиент обращается к Supabase через `@supabase/supabase-js`. Базовый адрес берётся
из `EXPO_PUBLIC_SUPABASE_URL`, ключ — из `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY`.
SDK хранит сессию и подставляет JWT пользователя в запросы.

Лента загружается через `.from('posts').select(...)`. Среди вложенных данных:

```text
post_media (id, media_type, storage_path, sort_order)
```

Пример нужного фрагмента ответа:

```json
{
  "id": "<POST_ID>",
  "post_media": [
    {
      "id": "<MEDIA_ID>",
      "media_type": "image",
      "storage_path": "<AUTHOR_ID>/<filename>.jpg",
      "sort_order": 0
    }
  ]
}
```

`storage_path` — точное имя объекта внутри бакета `post-media`, без домена,
без начального `/` и без префикса `post-media/`. Папка — ID автора файла,
а не пользователя, который сейчас просматривает ленту.

Из всех `post_media` страницы клиент собирает пути и передаёт их без изменения
в `storage.getPostMediaUrls(paths)`. Та же функция используется в профиле,
подробностях поста и при открытии редактирования.

## 2. Запрос временных ссылок

Фактический вызов клиента:

```ts
const { data, error } = await supabase.storage
  .from('post-media')
  .createSignedUrls(paths, 600);
```

Срок действия ссылок — 600 секунд (10 минут). Для пустого массива путей клиент
сразу возвращает пустой словарь и не обращается в Storage.

HTTP-эквивалент существенной части запроса SDK:

```http
POST <SUPABASE_URL>/storage/v1/object/sign/post-media
apikey: <PUBLISHABLE_KEY>
Authorization: Bearer <USER_ACCESS_TOKEN>
Content-Type: application/json
```

```json
{
  "paths": ["<AUTHOR_ID>/<filename>.jpg"],
  "expiresIn": 600
}
```

Ожидаемый сырой ответ Storage — массив, в котором поле ссылки называется
**`signedURL`** (важен регистр):

```json
[
  {
    "path": "<AUTHOR_ID>/<filename>.jpg",
    "signedURL": "/object/sign/post-media/<AUTHOR_ID>/<filename>.jpg?token=<TOKEN>",
    "error": null
  }
]
```

Установленный SDK преобразует относительный `signedURL` в полный `signedUrl`:

```ts
signedUrl: datum.signedURL
  ? encodeURI(`${this.url}${datum.signedURL}`)
  : null
```

Здесь `this.url` — адрес Storage: `<SUPABASE_URL>/storage/v1`.
Приложение читает уже **`data[i].signedUrl`**, после преобразования SDK.
Если сырой `signedURL` пуст или отсутствует, SDK устанавливает `signedUrl: null`.
Возвращать только поле `signedUrl` вместо `signedURL` в сыром HTTP-ответе
недостаточно для этого клиента.

## 3. Что происходит с пустой ссылкой

В `getPostMediaUrls` сейчас проверяется общая ошибка запроса, затем строится
словарь «путь → URL»:

```ts
if (error) throw error;

const result: Record<string, string> = {};
for (const item of data) {
  if (item.signedUrl && item.path) result[item.path] = item.signedUrl;
}
return result;
```

**Недочёт клиента:** индивидуальный `item.error` не обрабатывается.
Успешный HTTP-запрос может вернуть ошибку отдельного файла внутри массива;
такой элемент без ссылки просто пропадёт из словаря.

При подготовке карточки клиент сортирует медиа по `sort_order`, ищет ссылки
по исходному `storage_path` и отбрасывает пустые значения:

```ts
images: [...post.post_media]
  .sort((a, b) => a.sort_order - b.sort_order)
  .map((media) => urls[media.storage_path])
  .filter((url): url is string => Boolean(url))
```

Поэтому `path` в ответе подписания должен совпадать с запрошенным
`storage_path`. Иначе даже непустая ссылка не будет найдена.

`PostCard` отображает только первое доступное фото (`images[0]`):

```tsx
{cover ? (
  <Image source={{ uri: cover }} style={styles.cover} resizeMode="cover" />
) : null}
```

Дополнительные заголовки авторизации в `Image` не передаются: доступ к файлу
должен обеспечиваться токеном в подписанном URL. Если все ссылки исключены,
блок изображения не рисуется вообще. Это отличается от случая, когда URL
непустой, но загрузка самого файла по нему завершается ошибкой.

## 4. Как путь появляется при публикации

1. Клиент формирует имя `<USER_ID>/<timestamp>-<random>.<extension>`.
2. Читает локальное фото через `fetch(fileUri)` → `arrayBuffer()`.
3. Загружает данные через `.storage.from('post-media').upload(path, body, { contentType })`.
4. Берёт `data.path` из результата загрузки.
5. Записывает этот путь в `post_media.storage_path` вместе с `post_id`,
   `media_type` и `sort_order`.

Таким образом, в таблицу не записываются ни публичный URL, ни временная ссылка.
Для фото клиент поддерживает JPEG, PNG и WebP.

## 5. Аватары — отдельный поток

Для аватара клиент читает `profiles.avatar_path`. Если путь заполнен:

```ts
supabase.storage.from('avatars').getPublicUrl(path).data.publicUrl
```

URL строится локально, отдельного запроса за ссылкой нет. Клиент ожидает
публичный бакет `avatars`, как указано в документации проекта. Получение
`publicUrl` само по себе не проверяет наличие файла и доступность бакета.
При пустом `avatar_path` интерфейс показывает заглушку.

Если проблема относится именно к аватару, проверять нужно `avatar_path`,
наличие файла и публичную доступность `avatars`, а не подписывание `post-media`.

## 6. Что проверить на бэкенде

Для одного конкретного поста, у которого пропадает фото:

1. Возвращается ли запись `post_media` при чтении под JWT зрителя.
   Если `post_media: []`, запрос подписания этого файла вообще не произойдёт.
2. Заполнен ли `storage_path` и совпадает ли он с именем существующего объекта
   в бакете `post-media`. Нет ли полного URL, лишнего префикса или `/` в начале.
3. Доступно ли чтение объекта и создание подписанной ссылки под JWT этого
   пользователя. Проверить политики `SELECT` для `storage.objects`.
   Проверка с `service_role` не подтверждает доступ обычного пользователя.
4. Для общей ленты проверить отдельно собственное фото и фото другого автора:
   права загрузки только в собственную папку не должны автоматически означать,
   что зрителю разрешено читать только собственные фото. Правила чтения должны
   соответствовать разрешённой видимости постов.
5. Снять сырой ответ пакетного `/object/sign/post-media`: HTTP-статус и
   `path`, `signedURL`, `error` каждого элемента. Даже при успешном HTTP-статусе
   проверить индивидуальные ошибки.
6. Убедиться, что успешный элемент содержит относительный `signedURL` ожидаемого
   формата, а `path` совпадает с запрошенным значением.
7. Открыть полный URL сразу после выдачи: он должен возвращать изображение
   без дополнительного заголовка Authorization. Если URL непустой, но файл
   недоступен, отдельно проверить HTTP-ответ загрузки и срок действия ссылки.

Это направления проверки, а не установленная причина сбоя.
После диагностики на клиенте следует отдельно добавить обработку ошибок
элементов, чтобы проблемы подписания не скрывались как отсутствие фото.

## 7. Какие данные нужны для точного вывода

Передать по одному воспроизводимому случаю:

- ID поста, ID медиа и `storage_path`;
- собственный это пост или чужой для пользователя, выполнившего запрос;
- тело запроса подписания, HTTP-статус и сырой ответ;
- при непустой ссылке — HTTP-статус загрузки самого файла;
- время запроса и окружение.

JWT, ключи и значение `token` в подписанной ссылке в пересылаемых логах
заменить на `<REDACTED>`.
